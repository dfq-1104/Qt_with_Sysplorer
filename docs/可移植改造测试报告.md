# 两端纠错与实际验收记录

本文保留 R3/R4 外部模型阶段的历史记录。R5 内置模型的当前交付状态见《内置模型交付测试报告.md》，部署步骤见《可移植部署说明.md》；下文旧阶段的阻塞结论不代表 R5 当前状态。

发布标识：20261108-file-access-r3。日期：2026-11-08。

## 结论

远程 2026b 的 DLL 加载阻塞已修复，用户更新后确认 READY；客户端到实际虚拟机的上传、加载、翻译、求解、调参、下载、回放及停止测试已通过。

本机持续 UTF-8 失败已取得「进程读取内容不同」的直接证据：失败窗口读取 18,096 字节、哈希 01f02ff1…，独立检查同一路径为 14,000 字节、哈希 e03bd363…；两次及后续失败记录一致。失败进程加载 TianYu/InteKEY 文件加密模块，新 R3 普通用户窗口仍读取 18,096 字节，前 8 字节 cbd5d6ddcdacd4aa 按 GBK 解码为「苏州同元」，而正常模型前 8 字节为 7061636b61676520（package 和空格）。已确认读到不同的文件表示；保护策略的来源及应用授权仍需管理员或同元支持确认。不能归结为原模型编码错误，也不能宣称本机实际仿真已修复通过。

当前为候选交付；本机实际 2026a 最终 EXE 在测试启动上下文中已完成求解，但普通用户启动窗口的读取权限与日常全流程尚未通过，因此不标记两端完整可交付。没有自动更新安装目录、关闭用户程序、调整安全策略或更换访问凭据。

## 修复与证据

1. 模型读取记录实际路径、长度、哈希、错误位置、发布标识、进程、已加载文件访问模块及最多 8 字节十六进制签名，不记录完整模型或密钥。检测无效 UTF-8 且存在相关模块时提示核查明文读取权限，不自动解密或委托其他程序代读。
2. 新的普通 Qt 窗口存活约 4 分钟后点击加载，读取用户失败时同一路径，得到合法 14,000 字节及正确哈希。随后按预期报故意不存在的宿主；没有启动真实宿主。这排除了「只要长时间运行就必然校验失败」，但不替代原失败窗口的权限恢复验证。证据 logs/file-access-r2/long-lived-ui/result.json。
3. 2026b 缺失旧插件静态导入 SetWorkPath(const string&)；该宿主实际导出多一个 void* 上下文参数的版本。未猜测该上下文含义；插件取消改写全局 WorkPath，使用已存在的代码/结果/求解器/进程目录隔离并恢复。新 DLL 不再包含 SetWorkPath 导入，直接依赖在 2026a 只读检查通过。
4. 用户实际更新 2026b 后，新 DLL SHA-256 为 412076622D4966657ECF0BC195A42A4B9B07CBE4554E17AD5014D27190193EA6，Check-Server 返回 READY。客户端实际认证和就绪查询同样通过。原 remote.ini、端口、任务目录和凭据保留。
5. 后台任务存在且控制器 Idle 时等待初始化；确认运行控制器或插件活动任务才报告繁忙。发现记录临时被占用时，等待已核验存活的目标实例，避免额外启动。繁忙实例隔离规则保留。
6. 服务器检查始终写无密钥诊断，区分未运行、未加载插件、无状态记录、配置视图不一致、禁用、监听失败、后台等待及引擎未就绪。新增双击依赖检查与仅更新插件入口。
